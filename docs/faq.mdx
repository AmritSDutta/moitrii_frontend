# FAQ

## Every page returns 500 in dev with `EvalError: Code generation from strings disallowed`

**Symptom:** `npm run dev` starts, but every route responds with HTTP 500 and the server logs:

```
EvalError: Code generation from strings disallowed for this context
    at (middleware)/./src/middleware.ts
```

Next.js may also warn: *"You are using a non-standard `NODE_ENV` value in your environment."*

**Cause:** `NODE_ENV` is set to `production` in your environment — most often a system-wide variable. Next.js disables `eval` inside its edge sandbox whenever `NODE_ENV === "production"`:

```js
// next/dist/server/web/sandbox/context.js
codeGeneration: process.env.NODE_ENV !== "production"
  ? { strings: true, wasm: true }
  : undefined,
```

Because `src/middleware.ts` runs inside that sandbox, and the dev middleware bundle uses `eval`, the middleware fails to evaluate and the request never reaches a page.

**Fix:** run the app through the npm scripts, which pin the correct value with `cross-env`:

```bash
npm run dev   # cross-env NODE_ENV=development next dev
```

If you invoke `next dev` directly or add a new script, set it yourself:

```bash
npx cross-env NODE_ENV=development next dev
```

Unsetting the system-wide `NODE_ENV=production` removes the root cause entirely.

## `npm install` deletes dev dependencies

**Symptom:** After `npm install`, packages such as `vitest`, `tailwindcss`, or `typescript` are gone from `node_modules`, and `npm run test` / `npm run lint` fail.

**Cause:** npm is configured with `omit=dev`, which it inherits automatically from a global `NODE_ENV=production` — the same root cause as the 500s above.

**Fix:** install with dev dependencies included:

```bash
npm install --include=dev
```

## Tests fail with `act(...) is not supported in production builds of React`

**Symptom:** UI tests throw `Error: act(...) is not supported in production builds of React` as soon as `render()` is called.

**Cause:** React resolves to its **production** build, because `NODE_ENV=production` is set when the test runner boots.

**Fix:** `vitest.config.ts` already forces the test environment via `test.env`:

```ts
test: {
  env: { NODE_ENV: "test" },
  // ...
}
```

If you run Vitest from another entry point (a custom script, an IDE runner), make sure `NODE_ENV` is not `production`.

## Where do the tests live, and how do I run them?

Two tiers run under one config:

| Tier | Location | Environment | What it covers |
|------|----------|-------------|----------------|
| UI | `src/**/*.test.{ts,tsx}` | `jsdom` | Components/pages with `convex/react` and auth hooks mocked |
| Convex | `convex/**/*.test.ts` | `edge-runtime` | Real functions via `convex-test` against an in-memory backend |

```bash
npm test          # run both projects once
npm run test:watch  # watch mode
```

## Convex functions are missing types / `_generated` is empty

**Symptom:** Imports from `convex/_generated/api` fail, or the app cannot resolve any Convex function.

**Cause:** `convex/_generated/` is gitignored, so a fresh clone has no generated client until Convex codegen runs.

**Fix:** start the Convex dev server once (or run codegen) to generate it:

```bash
npx convex dev
```

## Why are subscriber emails and agent notifications sent via different providers?

Moitrii uses a **dual-channel messaging separation**:
- **Brevo (`convex/emails/brevo.ts`):** Handles marketing, subscriber welcome emails, and batch weekly lifestyle digests. These are platform-wide broadcasts directed to users on the `subscribers` list.
- **AgentMail (`convex/ai/agentMail.ts`):** Handles 1:1 personal agent deliverables. Every user has a dedicated personal companion (`Moitrii Companion`) with its own virtual inbox (`agent-...@agentmail.to`). Research deliverables are delivered directly from the agent's identity to the user's email, maintaining context and personalization.

## How does Moitrii handle user data privacy and PII anonymization?

To ensure strict privacy and future anonymization readiness:
1. **Isolated PII:** Real user names and personal emails exist solely in the `users` table.
2. **Generic Companion Personas:** The `agents` table stores only persona name `"Moitrii Companion"` and a generated AgentMail address. It never stores the user's real name or email.
3. **Opaque References:** All other tables (`requests`, `content`, `userInterests`) reference users only through opaque database IDs (`userId: v.id("users")`).

## How does account deactivation (`users.isActive: false`) work?

Every user record contains an `isActive` boolean flag (defaulting to `true`). In the event of a dispute, abuse report, or account freeze:
- An admin can invoke `setUserActiveStatus(userId, false)`.
- Scheduled agent wake cron jobs immediately skip the user's agent.
- `createRequest` mutations and profile edits reject further actions with an error.
- All existing data remains securely stored until the dispute is resolved.
